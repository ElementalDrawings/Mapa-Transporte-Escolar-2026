# 1. ARQUITECTURA: HIGH-COHESION & EVENT-DRIVEN

* **Decoupling via Events (El Toque Maestro):**
    * **Regla de Oro:** La lógica central (Core/Entidades) NUNCA debe ejecutar efectos secundarios externos directamente (UI, Red, Disco, Audio).
    * **Mecanismo:** El Core *registra* un cambio de estado o evento (ej: `ItemEquipped`, `TransactionCompleted`, `FileProcessed`).
    * **Dispatcher:** El sistema orquestador guarda el estado y *luego* despacha los eventos. Esto desacopla totalmente la lógica de las consecuencias.

* **Modular Design (Aislamiento):**
    * El código debe organizarse en módulos autocontenidos (Vertical Slices o Systems). Un cambio en el módulo "A" no debe romper el módulo "B".

# 2. PATRONES DE CÓDIGO (EXCELENCIA TÉCNICA):

* **Functional Core, Imperative Shell:**
    * Mantén la lógica de negocio/juego pura (sin I/O) tanto como sea posible. Recibe input, calcula, retorna nuevo estado.
    * Solo la capa de "Shell" (Controladores, Managers, Systems) gestiona la infraestructura o el motor.

* **Parse, Don't Validate + Type Safety:**
    * Usa el sistema de tipos para impedir estados inválidos. No uses primitivos (`string`, `int`) para datos con significado específico; usa tipos dedicados o Value Objects.
    * Transforma la entrada insegura en tipos seguros en la frontera del sistema.

* **Result Pattern / Explicit Flow:**
    * Evita excepciones para el flujo de control lógico. Usa estructuras de retorno explícitas (`Result<Success, Failure>`) para que los errores sean manejados obligatoriamente por el consumidor.

# 3. TESTING STRATEGY (REALISMO):

* **Sociable/State-Based Tests:**
    * Prioriza tests que verifiquen el comportamiento real del módulo sin depender de infraestructura pesada (DBs reales, Renderizado gráfico).
    * Usa implementaciones falsas (Fakes) en memoria para las dependencias externas.
    * El test debe verificar: 1) El cambio de estado interno correcto, 2) Que se emitieron los eventos/señales adecuados.
